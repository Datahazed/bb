How competitors handle extensibility

Ten competitors, sorted by how they surface skills, scheduled runs, plugins, and MCP servers. Some unify capability discovery into one hub (Cursor, Roo, Kilo, Cline); others ship real scheduled automations (Cursor, Devin, Tembo, Superset, Factory, Terragon). Almost no one does both in one place — and no one makes it card-based.

The opening for bb. The category is converging on unified extensibility hubs — Cursor’s “Customize” page is the most complete, and Roo/Kilo unified MCP + modes. But those hubs are filtered chip-tab lists, not card overviews, and none fold scheduled automations — with run history — into the hub (even Cursor keeps Automations on a separate page). A card-based, manage-first hub that treats automations as a first-class kind is the unclaimed combination — and bb already owns every primitive.

Cursor and Multica come closest — Cursor unifies a chip-tab “Customize” list but keeps Automations on a separate page; Multica bundles reusable skills + cron/webhook autopilots, but as an issue board (“agents as teammates”), not a card-based capability hub. Roo/Kilo unify capability discovery but have no scheduler; Devin/Tembo/Superset/Factory/Terragon schedule but scatter their surfaces. bb’s proposal is still the only card-based hub that treats skills, automations, and plugins as one kind-system — automations included.
The products, in brief

Conductor conductor.build

Parallel isolated workspaces on macOS. Strong status lifecycle (backlog→done) but no extensibility hub — slash commands are files, MCP is inherited config. docs

Emdash github · YC W26

The closest to a hub: a “Library” unifies Prompts + Skills + MCP as catalog cards with cross-agent sync — but Automations and agent-plugins live elsewhere. skills · MCP

Superset superset.sh

The strongest scheduler (RFC-5545 RRule, Pause / Run-now / history, CLI/MCP-dispatchable) — but run outcomes aren’t shown and skills/MCP have no UI. automations

Tembo tembo.io

Pivoted from Postgres to orchestration. Dashboard-uploaded Skills, schedule/webhook Automations, and a suggested-MCP gallery — three separate surfaces. changelog

Devin Cognition

Most mature: Playbooks (+ Community Gallery), Knowledge, a card-based MCP Marketplace (one-click OAuth), and a Schedules page — each its own Settings sub-page. MCP

Factory factory.ai · Droids

A real plugin marketplace (Browse/Installed/Marketplaces) bundling skills+commands+droids+MCP+hooks, plus a 40+ MCP registry and cron automations — but split across per-type CLI modals. plugins

Cline cline.bot

Pioneered the one-click MCP marketplace (app-store: categories, featured, ratings/downloads, auto-install) — but MCP-only; modes are just Plan/Act; orchestration is a separate Kanban app. MCP store

Roo Code shut down May 2026

Had the clearest unified marketplace — one tabbed panel listing MCPs and Modes with search, type filter, and “installed only.” The best precedent — but the extension was retired for a cloud pivot. marketplace

Kilo Code kilo.ai

Classic era unified Skills + MCP + Modes in one marketplace (Roo lineage); the 2026 rebuild fragmented it and pushed MCP back toward config files. marketplace repo

Cursor Cloud Agents

The most complete unified hub: a 3.9 “Customize” page spans Plugins / MCPs / Skills / Subagents / Rules / Commands / Hooks with search, marketplace, and scope — plus cron Automations. But it’s a chip-tab list, and Automations sits on its own page, outside the hub. automations

bb — the opening this proposal

bb already has skills, automations, plugins, and MCP (via connect). The unmade move: one Tools entry, one card idiom, one status system — a manager and a future marketplace, scheduler included.

Where bb’s Tools hub wins
1
Automations belong in the hub, with real run outcomes

Every unified hub (Cursor, Roo, Kilo, Cline) omits scheduling; every scheduler (Cursor, Superset, Devin, Tembo, Factory, Terragon) puts it on a separate page — and Superset can’t even show a run’s success/failure. A bb automation card + detail with live status, pause, and full run history inside the same hub is unmatched. — all fourteen

2
Manage what you own, not just browse a store

The marketplaces are discovery surfaces (install MCP/modes). bb’s hub leads with your installed skills, automations, and plugins as one uniformly-managed set — scope, enable/disable, edit — then adds browse. — Roo, Cline, Kilo

3
Config files become first-class cards

Slash commands as .md files (Conductor, Superset) and MCP as config (Kilo rebuild) mean “edit a file and hope.” bb makes each a browsable card with status and scope. — Conductor, Superset, Kilo

Three ideas worth borrowing
A
Cline / Devin one-click install → the “browse & add” state

App-store cards with ratings, one-click install, and auto-OAuth are exactly Direction A’s proposed marketplace grid — adopt for the future Connections (MCP) kind.

B
Cursor’s scope switcher + Roo’s “installed only” filter

Cursor’s personal / team / workspace scope switch and Roo’s type filter + “installed only” toggle are the cleanest precedents for switching kinds and separating installed from browse within one hub.

C
Superset RRule + Devin Run-now + real history

Pair a true recurrence primitive with Pause / Run-now / run-once and a first-class run log — the automation detail page the directions already sketch, done better than any single competitor.
